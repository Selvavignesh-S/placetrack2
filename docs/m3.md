## 2. Coordinator workflow

### 2.1 Status changes

```text
APPLIED ──► SHORTLISTED ──► SELECTED     (SELECTED also sets student.placed = true)
   │              │
   └──► REJECTED ◄┘                      WITHDRAWN is the student's action (M2), never the coordinator's
```

`ApplicationService.updateStatus(applicationId, next)`:
1. Load the application (404 if missing).
2. Check the move is allowed; otherwise `ApplyException("Cannot move an application from APPLIED to SELECTED")`.
3. Set the new status. If it is SELECTED, also set `student.placed = true`.
4. No `save()` call: inside `@Transactional` Hibernate writes both changes at commit (dirty checking).

The page only shows the buttons for allowed moves, but the service checks again, because anyone can send a POST
by hand (tested: posting `status=WITHDRAWN` or skipping SHORTLISTED is refused).

### 2.2 The transaction demo (UC18, report chapter 8)

Selecting a student changes **two rows in two tables** (`applications.status` and `students.placed`). Both must
change together or not at all. To prove it:

1. In `ApplicationService.updateStatus`, temporarily add this line **after** `setPlaced(true)`:
   ```java
   if (next == ApplicationStatus.SELECTED) throw new RuntimeException("demo: crash after both changes");
   ```
2. Restart, log in as `coord1`, open the Zephyr Software Engineer Trainee applicants and click **Select** for
   Rohan Das (SHORTLISTED). You get the error page.
3. In the H2 console:
   ```sql
   SELECT A.ID, A.STATUS, S.REG_NO, S.PLACED FROM APPLICATIONS A JOIN STUDENTS S ON S.ID = A.STUDENT_ID;
   ```
   Rohan is still SHORTLISTED and `PLACED` is still `FALSE`: the RuntimeException rolled back **both** changes.
4. Screenshot the error and the query result (`m3-04`, `m3-05`), then **remove the line** and restart.

### 2.3 Profile (and overposting protection)

`ProfileController` has a `@ModelAttribute("student")` method that loads the logged-in student from the database
before every request. On POST, Spring copies the form fields onto that loaded object, but `@InitBinder` allows only
`fullName`, `department`, `cgpa`, `backlogs`. So `email`, `regNo`, `password` and `placed` keep their stored values,
even if someone adds them to the request (tested). After saving, a new `SessionUser` is stored so the navbar shows
the new name. Validation still applies: CGPA 11 is refused and nothing changes.

Report note: CGPA and backlogs are self-declared here; a real system would have the coordinator verify them.

### 2.4 Dashboard

| Number | Comes from |
| --- | --- |
| Students | `studentRepository.count()` (free CRUD method) |
| Placed | `countByPlacedTrue()` (derived query: `select count(*) ... where placed = true`) |
| Open drives | `findOpenDrives(today).size()` (M1's HQL) |
| Applications per drive | M1's HQL `GROUP BY` with `left join`, so drives with 0 applications still appear |

The `GROUP BY` query returns `List<Object[]>` (`[companyName, roleTitle, count]`), read in Thymeleaf as
`row[0]`, `row[1]`, `row[2]`.

## 3. REST API (report chapter 10)

### 3.1 Endpoints

| Method + path | Body | Success | Errors |
| --- | --- | --- | --- |
| `GET /api/drives` | – | `200` list of open drives | – |
| `GET /api/drives/{id}` | – | `200` one drive | `404` |
| `POST /api/companies` | `{"name", "sector"}` | `201` the new company | `400` missing name or duplicate |
| `POST /api/applications` | `{"studentId", "driveId"}` | `201` the new application | `400` with `error` and `reasons`; `404`; `503` eligibility service down |
| `GET /api/students/{id}/applications` | – | `200` list | – |

Real responses from the test run:
```text
POST {"studentId":3,"driveId":2}  → 201  status APPLIED (no password hash anywhere in the JSON)
POST the same again               → 400  {"error":"You have already applied to this drive","reasons":[]}
POST {"studentId":4,"driveId":2}  → 400  {"error":"You are not eligible for this drive",
                                          "reasons":["CGPA 7.2 is below the required 7.5","Backlogs 1 exceed the limit of 0"]}
POST {"studentId":5,"driveId":2}  → 400  {"error":"You are already placed, so you cannot apply to more drives","reasons":[]}
POST {"studentId":3}              → 400  {"error":"Validation failed","fields":{"driveId":"must not be null"}}
GET  /api/drives/99               → 404  {"error":"Drive 99 not found"}
POST while the service is down    → 503  {"error":"Eligibility check unavailable, try later"}
```

### 3.2 How it works

- `@RestController` = `@Controller` + `@ResponseBody`: return values are written as **JSON** (by Jackson), not
  looked up as Thymeleaf templates.
- `@RequestBody` + `@Valid`: Jackson turns the JSON into an `ApplyRequest` record, then Bean Validation checks
  `@NotNull`; a failure becomes `MethodArgumentNotValidException`.
- `@ResponseStatus(HttpStatus.CREATED)`: a successful POST answers **201 Created** instead of 200.
- `ApiErrorHandler` (`@RestControllerAdvice(assignableTypes = ApiController.class)`): one place that maps each
  exception to a status code and a JSON body. It applies only to the API, so the HTML pages keep their error page.
- The API **reuses the same services** as the web pages (`ApplicationService.apply`), so every rule, the
  eligibility call, `@Transactional` and the AOP audit log apply to the API too. Only the "view" is different.
- `User.password` has `@JsonIgnore`, so password hashes never appear in API responses (tested).
- `POST /api/companies` sets `id` to `null` before saving, so an `"id"` in the body cannot overwrite an existing
  company (tested).

### 3.3 Known shortcut (say it in the viva)

The API has **no login** and trusts `studentId` from the body, so it is easy to test in Postman. A real system would
take the student from the session (like the web pages do) or from a token such as a **JWT** sent in the
`Authorization` header, and would not accept a student id from the client.

### 3.4 REST principles

| Principle | In PlaceTrack |
| --- | --- |
| Resources with URLs | `/api/drives`, `/api/drives/2`, `/api/students/3/applications` |
| HTTP methods carry the meaning | GET reads, POST creates |
| Stateless | Each request carries everything needed (here: ids in the URL or body) |
| Status codes | 200 OK, 201 Created, 400 Bad Request, 404 Not Found, 503 Service Unavailable |
| Representation | JSON |

**Idempotent** means repeating the request has the same effect as sending it once. GET is idempotent (reading twice
changes nothing). POST is not (a second apply is a new attempt; we refuse it with 400). PUT and DELETE are
idempotent; PATCH is usually not.

### 3.5 Web services and REST vs SOAP

A **web service** is software that offers its functions to other programs over the network using standard formats
(HTTP, JSON, XML), independent of the programming language. Our eligibility service is one; the `/api` endpoints are
another.

| | REST | SOAP |
| --- | --- | --- |
| What it is | An architectural style using plain HTTP | A protocol with strict rules |
| Message format | Usually JSON (also XML, text) | Always XML inside an "envelope" |
| Contract | None required (often OpenAPI/Swagger docs) | WSDL file describes every operation |
| Transport | HTTP | HTTP, also SMTP, JMS … |
| Operations | HTTP methods on resources (GET /drives) | Named operations (`getDrives`) all sent with POST |
| Size / speed | Light, fast, easy to cache | Heavier, more parsing |
| Built-in standards | Few | WS-Security, WS-ReliableMessaging, transactions |
| Typical use | Web and mobile apps, microservices (like ours) | Banking, government, legacy enterprise systems |

### 3.6 Postman

- **Collection** = saved requests in folders: `postman/PlaceTrack.postman_collection.json`.
- **Environment** = variables (`{{baseUrl}}`, `{{eligUrl}}`) so the same requests work on another machine or port.
- **Tests** tab = JavaScript checks run after each response, e.g.
  `pm.test("Status is 201", () => pm.response.to.have.status(201));`
- **Collection Runner** runs a whole folder and shows pass/fail per test (screenshot this for the report).

| Folder | Requests | Notes |
| --- | --- | --- |
| 00 Eligibility service | 5 | Port 8081 directly (M1) |
| 01 Drives and companies | 5 | List, one, 404, create (random name, so re-runnable), 400 |
| 02 Applications | 7 | Needs fresh seed data: delete `data/` and restart first |

### Monolith vs microservices (and where PlaceTrack sits)

See `docs/m1.md` section 8.3 for the full table. PlaceTrack is **mostly a monolith** (one main app owns all pages
and data) **with one job extracted as a microservice** (eligibility). That is a common, realistic first step.

### Spring Cloud

Spring Cloud is a set of Spring projects for the problems that appear when an application is split into many
services. We use none of them, on purpose, but each one maps to something we did by hand:

| Spring Cloud feature | What it does | In PlaceTrack today | With Spring Cloud |
| --- | --- | --- | --- |
| **OpenFeign** | Declarative REST client | `EligibilityClient` builds the call with `RestTemplate` | An interface with `@FeignClient` and `@PostMapping("/eligibility/check")`; Spring generates the HTTP code |
| **Eureka** (service discovery) | Services register by name, clients look them up | URL hard-coded in `eligibility.url` | Call `http://eligibility-service/...`; Eureka finds a running instance |
| **Spring Cloud Gateway** | One entry point that routes to services | Browser talks to each port directly | Single port; routing, auth and rate limits in one place |
| **Config Server** | Central configuration for all services | Each project has its own `application.properties` | Properties served from one Git repo |
| **Resilience4j** (circuit breaker) | Stops calling a failing service for a while, uses a fallback | Hand-written timeouts + "try later" message | `@CircuitBreaker` with a fallback method; failures are counted automatically |

The one we would add first is **OpenFeign** (replaces `EligibilityClient`), then **Resilience4j** (replaces our
manual failure handling).

## 5. DevOps (report chapter 13)

**DevOps** is a way of working where development and operations work together, using automation so that code is
built, tested and released often, quickly and reliably.

| Practice | Meaning | In this project |
| --- | --- | --- |
| Version control | Every change is recorded and shareable | Git + GitHub, one branch per member, pull requests into `main` |
| Build automation | One command builds and tests the code | Maven: `./mvnw clean verify` |
| Automated testing | Tests run on every build | 31 JUnit tests across both projects, Postman collection tests |
| Continuous Integration (CI) | Every push is built and tested automatically | Not set up (would be a GitHub Actions workflow running `./mvnw verify`) |
| Continuous Delivery/Deployment (CD) | Tested code is released automatically | Not in scope (would build a jar or Docker image and deploy it) |

| Tool | Purpose | Used here? |
| --- | --- | --- |
| Git | Version control | ✅ |
| GitHub | Hosting, collaborators, pull requests | ✅ |
| Maven (+ wrapper) | Build, dependencies, tests, packaging | ✅ |
| JUnit, Mockito, Postman | Testing | ✅ |
| GitHub Actions / Jenkins | CI/CD pipelines | Named only |
| Docker | Package an app with its runtime into a container | Named only |
| SonarQube | Code quality analysis | Named only |

**Advantages:** faster releases, fewer bugs reaching users (tests on every change), the same build on every machine,
easy rollback through Git history, and better teamwork.

**Maven lifecycle:** `validate → compile → test → package → verify → install → deploy`. Running a phase runs all
phases before it, so `./mvnw verify` compiles, runs the tests and builds the jar. `clean` deletes `target/` first.
`pom.xml` declares the project, its Java version, its dependencies and its plugins.

## 8. Viva questions and short answers

| Question | Answer |
| --- | --- |
| What is REST? | An architectural style: resources at URLs, HTTP methods for actions, stateless requests, standard status codes, usually JSON |
| `@RestController` vs `@Controller`? | `@RestController` returns data (JSON); `@Controller` returns a view name for a template |
| GET vs POST? | GET reads and is idempotent and safe; POST sends data to create or process something and is not idempotent |
| Why 201 and not 200 for apply? | 201 Created says a new resource was made |
| How does JSON become a Java object? | Jackson maps JSON fields to the record's components by name (`@RequestBody`) |
| What does `@Valid` do? | Runs the Bean Validation annotations before the method; failures become a 400 through our handler |
| What is `@RestControllerAdvice`? | A central exception handler for REST controllers that turns exceptions into JSON responses |
| Why does the API reuse `ApplicationService`? | One place for the rules; pages and API behave the same, and the aspect and transaction apply to both |
| Why is studentId in the body a problem? | Anyone could apply as anyone; real systems take the user from the session or a JWT |
| What is a web service? | Functionality offered to other programs over a network with standard protocols and formats |
| REST vs SOAP? | Light JSON over HTTP vs XML envelopes with a WSDL contract and WS-* standards (table above) |
| What are Postman collections, environments, tests? | Saved requests; variables per machine; JavaScript checks on each response |
| Monolith vs microservices? | One deployable app vs many small independent services; we have one app plus one extracted service |
| What is Spring Cloud? Which feature fits us? | Tools for distributed systems; OpenFeign would replace our client, Resilience4j our failure handling |
| What does the status-change transaction prove? | Status and `placed` are saved together; a crash after both changes rolls back both |
| What is DevOps? | Dev and Ops working together with automation: version control, automated build and test, CI/CD |
| What does `./mvnw clean verify` do? | Deletes old output, compiles, runs all tests, packages the jar |
| What is in `pom.xml`? | Project coordinates, parent (Spring Boot), Java version, dependencies, build plugins |
| Branch, commit, pull request, merge? | A branch is a separate line of work; a commit saves a change; a pull request asks to merge a branch into `main` after review |

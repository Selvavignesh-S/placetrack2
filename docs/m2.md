## 2. Routes

| Method + path | Who | What happens |
| --- | --- | --- |
| `GET /` | anyone | Not logged in → `/login`; student → `/student/drives`; coordinator → `/coordinator/drives` |
| `GET /login`, `POST /login` | anyone | Login form; on success the `SessionUser` goes into the session |
| `POST /logout` | logged in | Session destroyed, back to `/login` |
| `GET /register`, `POST /register` | anyone | Student sign-up |
| `GET /student/drives` | student | Drives whose deadline is today or later, with an "Applied" badge |
| `GET /student/drives/{id}` | student | Drive detail with Check and Apply buttons |
| `GET /student/drives/{id}/check` | student | Same page plus "You are eligible" or the list of reasons. Saves nothing |
| `POST /student/drives/{id}/apply` | student | Apply; success → My applications, refusal → back with the reasons |
| `GET /student/applications` | student | My applications with coloured status badges |
| `POST /student/applications/{id}/withdraw` | student | Withdraw (only APPLIED or SHORTLISTED) |

Logout is a POST (a form button), not a link, so another website cannot log you out with an image tag.

## 3. The apply flow (the heart of the project)

```text
Student clicks Apply
  → POST /student/drives/2/apply
  → LoginInterceptor: logged in? role STUDENT? yes → continue
  → StudentController.apply(driveId = 2, user from session)
  → ApplyAuditAspect starts timing                                   (AOP proxy)
  → @Transactional begins a database transaction                      (transaction proxy)
  → ApplicationService.apply(studentId, 2):
        1. load student and drive (404 if missing)
        2. student already placed?          → ApplyException "You are already placed ..."
        3. deadline passed?                 → ApplyException "The deadline for this drive has passed"
        4. already applied?                 → ApplyException "You have already applied to this drive"
        5. EligibilityClient → POST :8081/eligibility/check
              service down / too slow       → EligibilityUnavailableException
        6. not eligible?                    → ApplyException "You are not eligible ..." + reasons
        7. save Application(status APPLIED)
  → transaction commits (or rolls back on any exception)
  → aspect logs SUCCESS or BLOCKED with the time
  → controller: success → redirect to My applications with "Applied successfully"
                refusal → redirect back to the drive with the message and reasons (flash attributes)
```

Why this order: cheap checks in our own database come first; the network call to the other service comes last,
so it only happens when it is really needed.

Double-click protection: if two Apply clicks arrive together, both pass step 4, but the database's unique
(`student_id`, `drive_id`) constraint stops the second insert. We catch that and show "already applied".

## 4. Concepts, in plain words

### 4.1 MVC request flow
1. The browser sends a request to Tomcat (the web server inside Spring Boot).
2. **DispatcherServlet** (Spring's front controller) receives every request.
3. **Interceptors** run first (our `LoginInterceptor`).
4. The matching **controller** method runs, calls services, and puts data into the **Model**.
5. It returns a **view name** like `"student/drives"`.
6. The **view resolver** finds `templates/student/drives.html`; **Thymeleaf** fills it with the model data.
7. The finished HTML goes back to the browser.

### 4.2 Sessions and login
- HTTP forgets everything between requests. A **session** is server-side memory per browser, linked by the
  `JSESSIONID` cookie.
- After login we store `SessionUser(id, name, role)` in the session. Every later request can read it with
  `@SessionAttribute(SessionUser.KEY)`.
- `request.changeSessionId()` at login gives the browser a new session id, so an id someone stole *before*
  login is useless afterwards (protection against **session fixation**).
- **BCrypt**: passwords are stored as salted one-way hashes. At login, `passwordEncoder.matches(typed, hash)`
  hashes the typed password and compares. Nobody, not even us, can read the original password.
- The login error is always "Wrong email or password": we never say which one was wrong, so attackers cannot test
  which emails exist.

### 4.3 Interceptor (the role guard)
A `HandlerInterceptor` runs **before** the controller. `preHandle` returns `true` (continue) or `false` (stop).
We register it only for `/student/**` and `/coordinator/**`, so login, register and the CSS stay public.
We use this instead of full Spring Security because it is about 20 lines that we can explain completely.

### 4.4 Overposting protection (`@InitBinder`)
Spring copies every form field whose name matches a property. Someone could add `placed=true` or `id=1` to the
registration form by hand. `binder.setAllowedFields(...)` in `AuthController` lists the only fields that may be
copied, so extra fields are ignored. Tested: registering with `id=1&placed=true` creates a normal, unplaced student
and leaves user 1 untouched.

### 4.5 Post-Redirect-Get and flash attributes
After every POST we answer with a redirect, so pressing Refresh does not apply twice. Messages and reasons travel
across that redirect as **flash attributes**: stored in the session for exactly one request, then deleted.

### 4.6 `@Transactional`
- Spring wraps `ApplicationService` in a **proxy**. Calling `apply()` really calls the proxy, which begins a
  transaction, calls the real method, then **commits**; if a `RuntimeException` escapes, it **rolls back**.
- Our exceptions extend `RuntimeException`, so a refused apply saves nothing.
- **Dirty checking**: in `withdraw` we only call `application.setStatus(WITHDRAWN)`, no `save()`. Inside a transaction
  the entity is "managed": Hibernate remembers its original values and writes an `UPDATE` for anything that changed at
  commit time.
- Self-invocation trap: if a method calls another method **of the same class**, the call skips the proxy, so its
  `@Transactional` and aspects do not apply.

### 4.7 AOP: `ApplyAuditAspect`
| Term | In our code |
| --- | --- |
| **Cross-cutting concern** | Logging/auditing: needed in many places, not part of the business logic |
| **Aspect** | The `ApplyAuditAspect` class |
| **Join point** | One call of `ApplicationService.apply(...)` |
| **Pointcut** | `execution(* com.placetrack.service.ApplicationService.apply(..))`: which calls to catch |
| **Advice** | The `@Around` method `audit()`: code that runs around the call (`proceed()` runs the real method) |
| **Weaving** | Spring builds a proxy around `ApplicationService` at startup and routes calls through the advice |

Other advice types: `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing`. We use `@Around` because it can time
the call and see both success and exceptions.

### 4.8 Dependency Injection, BeanFactory and ApplicationContext
- **DI**: no class creates its collaborators with `new`. `ApplicationService` lists what it needs in its
  constructor (`StudentRepository`, `DriveService`, `ApplicationRepository`, `EligibilityClient`) and Spring passes
  them in. That keeps classes loosely coupled and makes testing easy: `ApplicationServiceTest` passes Mockito fakes
  into the same constructor.
- Why **constructor** injection rather than field (`@Autowired` on a field) or setter injection: the fields can be
  `final`, the object is never half-built, and tests can create it without Spring.
- **Bean scopes**: `singleton` (default, one shared object), `prototype` (new object each time), and for web apps
  `request` and `session`.

`demo/BeanFactoryDemo` real output:
```text
===== Part 1: BeanFactory (lazy) =====
1. Bean definition registered. Nothing created yet.
2. Calling factory.getBean("greeter")...
      -> Greeter constructor runs (bean created)
3. Hello from a Spring bean

===== Part 2: ApplicationContext (eager + dependency injection) =====
1. Beans registered. Calling context.refresh()...
      -> Greeter constructor runs (bean created)
2. refresh() finished: the Greeter was already created above, before any getBean call.
3. Hello from a Spring bean, injected into WelcomeService
```

| | BeanFactory | ApplicationContext |
| --- | --- | --- |
| What | The basic container interface | Extends BeanFactory with more features |
| Singleton creation | Lazy: when first requested | Eager: all at startup, so config errors appear immediately |
| Annotations (`@Autowired`, `@PostConstruct`), AOP | Not by itself | Yes (registers the post-processors automatically) |
| Events, i18n messages, environment/profiles | No | Yes |
| Used by | Very small or memory-limited setups | Practically every Spring app; Spring Boot creates one for us |

Run it: in the IDE open `BeanFactoryDemo` and click ▶ next to `main`.

### 4.9 Calling the other service, and failure handling (UC24)
- `RestTemplate.postForObject(url, body, EligibilityResult.class)`: Jackson turns the `Map` into JSON, sends it,
  and turns the JSON reply into an `EligibilityResult` record.
- **Timeouts**: 2 s to connect, 3 s to read. Without them, a hung service would freeze the student's page.
- Any `RestClientException` (connection refused, timeout, error reply) becomes `EligibilityUnavailableException`:
  the page shows "Eligibility check unavailable, try later" and nothing is saved.
- `EligibilityResult` is a **copy** of the service's response class, on purpose: microservices share only the
  JSON contract, never Java code.
- Spring Cloud alternatives (explain only): **OpenFeign** would replace `EligibilityClient` with an annotated
  interface; **Resilience4j** circuit breaker would stop calling a failing service for a while and use a fallback.

## 9. Viva questions and short answers

| Question | Answer |
| --- | --- |
| Walk through a request | Browser → DispatcherServlet → interceptor → controller → service → repository → model → Thymeleaf view → HTML |
| What is Post-Redirect-Get? | After a POST we redirect, so a refresh repeats only the harmless GET |
| How does login work? | Find user by email, `BCrypt.matches`, put `SessionUser` in the session, change the session id |
| Why `changeSessionId()`? | Prevents session fixation: an id known before login stops working |
| Why BCrypt and not plain text? | One-way, salted, deliberately slow hash: a leaked database does not reveal passwords |
| What does the interceptor do? | Runs before controllers; redirects guests to login and sends 403 for the wrong role |
| Why not Spring Security? | Too large to explain fully in our time; our 20-line interceptor covers what we need |
| Constructor vs field injection? | Constructor: `final` fields, no half-built objects, easy to test with mocks |
| BeanFactory vs ApplicationContext? | Lazy basic container vs eager full container with annotations, AOP, events (demo output above) |
| Bean scopes? | singleton (default), prototype, request, session |
| What is AOP? Name the parts | Separating cross-cutting code; aspect, advice, pointcut, join point, weaving through proxies |
| Why `@Around`? | It can time the call and sees both the result and exceptions |
| How does `@Transactional` work? | A proxy begins a transaction, calls the method, commits, or rolls back on a RuntimeException |
| What is dirty checking? | Hibernate saves changes to managed entities at commit without calling `save()` |
| What if the eligibility service is slow or down? | Timeouts (2 s / 3 s) → exception → "try later" message, nothing saved, audit logs BLOCKED |
| RestTemplate vs OpenFeign? | RestTemplate: we write the HTTP call. OpenFeign (Spring Cloud): declare an interface, the call is generated |
| What stops applying twice? | A service check, plus the database unique constraint for simultaneous clicks |
